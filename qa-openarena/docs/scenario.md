# scenario.md — 테스트 시나리오로 매치를 자동 실행하기

`run_qa.bat` 을 실행하면 게임이 켜지고, **시나리오에 적힌 조건 그대로 매치가 시작된다.**
맵이 로드되고 봇이 정해진 수만큼 정해진 실력으로 들어오며, 실험용 cvar 와 결함 주입 상태까지
맞춰진다. 사람이 메뉴에서 할 일이 없다.

이 문서는 시나리오 파일을 어떻게 쓰는지, 그리고 그 파일이 게임에서 어떻게 실행되는지를 담는다.

역할 분담:
- **이 문서**: 시나리오 파일 형식과 실행 원리.
- `docs/setup.md`: 게임 설치와 QVM 빌드 등 그 앞단 전체.
- `docs/explain.md`: 파이썬 쪽 데이터 흐름.
- `docs/process.md`: 왜 이렇게 만들었는지의 시간순 기록.

## 0. 문서 작성 규칙
- 기존 기록은 삭제하지 않는다. 내용이 바뀌면 취소선과 `[제거 YYYY-MM-DD: 사유]`를 남기고,
  새 내용을 아래에 `[추가 YYYY-MM-DD]`로 기록한다.
- 문서체는 평서형(~다)으로 통일한다.

## 1. 무엇을 푸는가

이전에는 `run_qa.bat` 이 게임을 띄우기만 했다. 게임은 메인 메뉴에서 멈추고, 사람이 맵을 고르고
봇을 넣어야 매치가 시작됐다. 여기서 두 가지 문제가 생긴다.

**재현이 안 된다.** 검출 결과는 매치 조건에 강하게 의존한다. 봇이 4마리인지 8마리인지, 실력이
1인지 5인지에 따라 이상탐지의 발사 비율이 통째로 달라진다. 그런데 그 조건이 사람의 손끝에만
있으면 세션 파일을 나중에 열었을 때 "이 결과가 어떤 조건에서 나왔는가"를 알 수 없다.
`qa/config.py` 에 판정 설정값을 모아 세션 요약에 함께 남긴 것과 정확히 같은 문제이고, 같은
해법이 필요하다. 조건을 파일에 적고, 그 파일을 실행하고, 그 파일을 결과와 함께 보관한다.

**시험을 반복할 수 없다.** README 의 검증 표에 있는 네 세션(정상·저중력·반동 증폭·봇 실력 최저)은
전부 손으로 조건을 맞춰 만든 것이다. 조건이 파일이 아니면 한 달 뒤에 같은 시험을 다시 돌릴 때
그때와 같은 조건이라는 보장이 없다.

## 2. 빠른 시작

`run_qa.bat` 위쪽에서 기본 시나리오를 고른다.

```bat
set "SCENARIO=scenarios\default.toml"
```

비워 두면 시나리오를 쓰지 않고 예전처럼 게임만 띄운다.

### 다른 시나리오로 돌리는 두 가지 방법

**(1) 명령줄로 넘긴다.** 파일 위쪽의 값 대신 이것이 쓰인다.

```
run_qa.bat scenarios\skill_low.toml
```

자주 쓰는 조합은 두 줄짜리 파일로 만들어 둔다. `run_qa.bat` 자체를 복사하지는 않는다.
복사본에는 나머지 200여 줄이 함께 복제되고, conda 경로나 포트를 고칠 때 한쪽만 고치면
두 실행이 조용히 달라진다. 검출 설정값을 `qa/config.py` 한곳에 모은 것과 같은 이유다.

```bat
@echo off
call "%~dp0run_qa.bat" scenarios\skill_low.toml
```

**(2) 게임을 켜 둔 채 바꾼다.** 서버·프론트엔드·게임이 이미 떠 있으면 이쪽이 빠르다.
데이터를 여러 조건으로 연달아 모을 때 쓴다.

```
python tools\apply_scenario.py scenarios\skill_low.toml ^
    --telemetry "%APPDATA%\OpenArena\qa\qa_telemetry.jsonl" ^
    --game "C:\game\openarena-0.8.8"
```

그다음 게임 콘솔(`~`)에서 한 줄이면 새 조건으로 매치가 다시 시작된다.

```
\exec qa_match.cfg
```

맵이 다시 로드되면서 텔레메트리가 잘리고, 서버는 그것을 새 매치로 보아 세션을 새로 연다.
**새 세션에는 바뀐 시나리오가 기록되고 이전 세션에는 이전 시나리오가 남는다.** 세션이 시작될
때 시나리오를 붙잡아 두기 때문이다(5절). 나중에 세션 요약의 `scenario.purpose` 만 봐도
어느 조건에서 모은 것인지 갈라낼 수 있다.

시나리오를 고치는 동안 게임을 켤 필요는 없다. 결과만 확인하려면 이렇게 한다.

```
python tools/apply_scenario.py scenarios/default.toml --game "C:\game\openarena-0.8.8" --dry-run
```

설치본에 어떤 맵과 봇이 들어 있는지 보려면 이렇게 한다.

```
python tools/apply_scenario.py --list --game "C:\game\openarena-0.8.8"
```

저장소에 들어 있는 시나리오는 넷이다.

| 파일 | 용도 | 무엇을 위한 조건인가 |
|---|---|---|
| `scenarios/default.toml` | `baseline` | 정상 플레이. 이상탐지 학습 데이터와 대조군을 뽑는다 |
| `scenarios/skill_low.toml` | `probe` | 봇 실력 최저. 이상탐지(②) 양성 검증 |
| `scenarios/inject_stuck.toml` | `probe` | 끼임 주입을 키로 토글. 하드 인바리언트(①) 양성 검증 |
| `scenarios/mixed_skill.toml` | `probe` | 봇마다 실력을 다르게 주는 방법의 예시 |

`baseline` 은 하나뿐이고 나머지는 전부 `probe` 다. 이 구분의 의미는 4절에 있다.

## 3. 시나리오 파일 형식

TOML 이다. 주석을 달 수 있고 파이썬 3.11 이상의 표준 라이브러리(`tomllib`)로 읽히므로 의존성이
늘지 않는다. 시나리오는 사람이 손으로 쓰면서 왜 그 값인지 옆에 적어 두는 파일이라 주석이 없는
형식(JSON)은 쓰기 어렵다.

### 최상단

| 키 | 기본값 | 뜻 |
|---|---|---|
| `name` | `"이름 없는 시나리오"` | 표시용 이름. 세션 요약과 게임 콘솔에 그대로 나온다 |
| `purpose` | `"hunt"` | 이 조건의 용도. `baseline` `probe` `hunt` 중 하나. 4절 참조 |
| `notes` | `""` | 메모. 생성된 cfg 의 머리말과 세션 요약에 들어간다 |

### `[match]` — 매치 조건

| 키 | 기본값 | 뜻 |
|---|---|---|
| `map` | 없음(필수) | 로드할 맵 이름 |
| `gametype` | `"ffa"` | `ffa` `tournament` `single` `team` `ctf` 중 하나, 또는 `g_gametype` 번호 |
| `maxclients` | `16` | 서버가 받을 최대 인원. 봇 수보다 커야 한다(사람이 한 자리를 쓴다) |
| `fraglimit` | `0` | 0이면 점수로 매치가 끝나지 않는다 |
| `timelimit` | `0` | 0이면 시간으로 매치가 끝나지 않는다 |
| `warmup` | `0` | `g_doWarmup`. 준비 시간 동안 봇이 얼어 있어 기본은 끈다 |

`gametype` 을 이름으로 받는 목록이 다섯 개뿐인 이유는, 그 뒤의 번호가 배포판마다 다르기
때문이다. 표에 없는 모드는 게임에서 확인한 번호를 숫자로 적는다. 모르는 이름을 조용히 0(FFA)
으로 떨어뜨리면 엉뚱한 모드로 시험하게 되므로 도구가 오류로 막는다.

**`fraglimit` 과 `timelimit` 은 0으로 둔다.** 0이 아니면 매치가 끝나고, 게임이 다음 맵을
로드하면서 텔레메트리 파일을 `FS_WRITE` 로 새로 열어 그 판의 기록이 사라진다. 점수판
구간에서는 봇이 움직이지 않아 발사 비율이 0이 되고, 그것이 실력 최저 봇과 같은 신호라
이상탐지가 오탐한다. 0이 아닌 값을 적으면 도구가 경고한다.

### `[roster]` — 봇 구성

| 키 | 기본값 | 뜻 |
|---|---|---|
| `count` | `0` | 봇 수. 이름을 적지 않으면 설치본의 봇 이름에서 순서대로 채운다 |
| `skill` | `3` | 자동으로 채울 때와 `[[roster.bots]]` 에서 생략했을 때의 실력(1~5) |
| `team` | `"free"` | 같은 방식의 기본 팀. `free` `red` `blue` |
| `keep_filled` | `false` | 봇이 빠지면 서버가 자동으로 채울지(`bot_minplayers`) |
| `spawn_stagger_ms` | `250` | 봇을 한 마리씩 띄우는 간격(밀리초) |

봇마다 실력을 다르게 주려면 이름을 하나씩 적는다.

```toml
[[roster.bots]]
name = "Sarge"
skill = 5

[[roster.bots]]
name = "Penguin"
skill = 1
```

`count` 와 함께 쓰면 적어 놓은 봇이 먼저 들어가고 모자란 만큼이 설치본에서 채워진다.
반대로 이름을 전부 적어 두면 `count` 를 쓰지 않아도 되고, 그때는 설치본 조사가 실패해도
시나리오가 그대로 동작한다. 저장소의 예시 시나리오가 그 형태다.

**같은 이름을 여러 번 적어도 된다.** 게임은 같은 캐릭터를 여러 마리 넣는다. 설치본의 봇
수보다 많은 인원으로 돌리고 싶을 때 쓴다. 텔레메트리는 이름이 아니라 엔티티 번호로 봇을
구분하므로 검출·집계·이상탐지 어디에도 영향이 없다.

`keep_filled` 를 켜면 `bot_minplayers` 가 봇 수만큼 설정된다. 오래 돌리는 학습용 세션에서
인원이 유지되는 이점이 있지만, **서버가 보충하는 봇의 실력은 `g_spSkill` 하나로 정해진다.**
봇별로 다른 실력을 준 시나리오에서는 보충된 봇만 실력이 달라지므로 기본은 꺼져 있다.

### `[cvars]` — 실험용 cvar

무엇이든 적을 수 있다. README 의 검증 표에 있는 교란 조건들이 여기에 해당한다.

```toml
[cvars]
g_gravity = 500      # 저중력
g_knockback = 1500   # 반동 증폭
g_spSkill = 1        # 서버가 보충하는 봇의 실력
```

### `[inject]` — 결함 주입기의 시작 상태

| 키 | 게임 cvar | 무엇을 만드는가 |
|---|---|---|
| `health` | `qa_inject_health` | 체력을 999로 고정 |
| `oob` | `qa_inject_oob` | x 좌표를 맵 밖으로 강제 |
| `fall` | `qa_inject_fall` | 콜리전을 제거해 바닥을 뚫고 떨어뜨림 |
| `stuck` | `qa_inject_stuck` | 위치를 한 점에 고정(이동 입력은 그대로 유지) |

적지 않은 주입기도 생성된 cfg 가 명시적으로 0으로 되돌린다. 앞 실행에서 켜 둔 값이 남아 있으면
이번 매치가 조용히 오염되고, 세션 요약만 봐서는 그 사실을 알 수 없기 때문이다.

`oob` 와 `stuck` 은 둘 다 위치를 조작하므로 동시에 켜면 서로 덮어쓴다. 도구가 오류로 막는다.

### `[keys]` — 시연용 키 바인딩

```toml
[keys]
F5 = "qa_inject_stuck 1"
F6 = "qa_inject_stuck 0"
```

매치 도중에 조건을 바꾸는 유일한 방법이다. 이유는 9절에 있다.

### `[player]`

| 키 | 기본값 | 뜻 |
|---|---|---|
| `spectator` | `true` | 사람을 관전으로 돌린다 |

기본이 `true` 인 이유는 결함 주입기가 아직 봇 한정이 아니라 사람에게도 걸리기 때문이다
(`docs/gamecode_instrumentation.md` 4절). 관전으로 빠져 있으면 주입이 시험 대상인 봇에게만 보인다.

### `[timing]`

| 키 | 기본값 | 뜻 |
|---|---|---|
| `wait_frames` | `150` | 맵 로드 후 봇을 넣기까지 기다릴 프레임 수 |
| `spectator_wait_frames` | `60` | 봇 투입 후 관전으로 돌리기까지 기다릴 프레임 수 |

봇이 들어오지 않으면 여기를 늘린다. 근거는 7절에 있다.

## 4. 용도(`purpose`)와 이상탐지의 관계

시나리오에서 가장 조심해야 할 항목은 **봇 실력**이다. 이상탐지(②) 오라클과 직접 얽혀 있기
때문이다. 이 절은 그 얽힘이 무엇이고 왜 `purpose` 라는 항목이 생겼는지를 담는다.

### 얽힘의 정체

② 오라클은 정상 플레이를 학습하고 거기서 벗어난 정도를 점수로 낸다. 여기서 **"정상"은
학습에 쓴 조건을 뜻하지 게임의 절대적 정상 상태가 아니다.** 모델은 특정 맵에서, 특정 봇
수로, 특정 실력으로 돌린 세션의 발사 비율과 체력 변화를 보고 "이것이 정상"이라고 배웠다.

그래서 봇 실력을 낮추면 ②는 이상을 잡는다. 실제로 100% 잡았고, 그 결과가 README 검증 표에
있다. 그런데 **그것은 게임에 버그가 있다는 뜻이 아니다.** 조건이 학습 때와 다르다는 뜻이다.
같은 숫자가 두 가지 전혀 다른 것을 뜻할 수 있다.

- 시험지에서 나온 100%: 오라클이 제대로 동작한다는 **좋은 신호**다.
- 정상 조건에서 나온 100%: 게임에 무언가 일어났다는 **나쁜 신호**다.

세션 요약에는 `anomaly_count` 라는 숫자 하나만 남는다. 조건을 함께 적어 두지 않으면 나중에
파일만 보고 둘을 구분할 수 없다.

### 그렇다면 실력 항목을 빼야 하는가

빼지 않는다. 두 가지 이유다.

**(1) 빼도 값은 사라지지 않는다.** 시나리오에 안 적으면 봇 실력은 게임의 기본값이나 앞서
설정한 값으로 정해지고, 그 값은 아무 데도 기록되지 않는다. 조건이 **암묵적이고 기록되지 않는
상태**가 되는데, 그것이 바로 시나리오 체계를 만든 이유였던 문제다. 값을 숨기는 것은 의존을
없애는 것이 아니라 보이지 않게 하는 것뿐이다.

**(2) 실력은 ②의 유일하게 검증된 시험지다.** 물리 파라미터 교란은 세 번 시도해 모두 실패했다
(README '설계에서 배운 것'). 약하면 봇이 적응해 행동이 그대로이고, 강하면 하드 규칙이 먼저
잡는다. 그 사이 지대에 있는 것이 봇 실력 하향뿐이었다. 이 항목을 빼면 ②를 검증할 방법이
사라진다.

### 그래서 무엇을 하는가

값을 빼는 대신 **그 값을 어떤 뜻으로 쓰는지를 함께 적는다.** 그것이 `purpose` 다.

| 값 | 뜻 | ②의 이상 판정을 어떻게 읽는가 |
|---|---|---|
| `baseline` | 이상탐지의 '정상'을 정의하는 조건. 학습과 대조군에 쓴다 | 오탐이다. 비율이 기준선(5%)보다 크게 높으면 모델을 다시 본다 |
| `probe` | 조건을 의도적으로 흔든 시험지 | 시험 통과 신호다. 반응하는 것이 정상이다 |
| `hunt` | 실제로 버그를 찾는 운용 조건 | 조사 대상이다. 이것이 평범한 해석이다 |

기본값은 `hunt` 다. 용도를 적지 않은 시나리오는 대개 그냥 돌려 보며 버그를 찾는 조건이고,
그때는 이상 판정이 조사 대상이라는 평범한 해석이 맞다. `baseline` 을 기본값으로 두면 주입이
켜진 시나리오가 오류로 막히고, `probe` 를 기본값으로 두면 진짜 버그 신호를 "시험 통과"로
잘못 읽게 된다.

도구가 하는 일은 셋이다.
- `baseline` 인데 결함 주입이 켜져 있으면 **막는다.** 기준 조건에 결함이 섞이면 모델이 그
  결함을 정상으로 배우고, 그 뒤로는 진짜 정상 플레이를 이상으로 판정하게 된다.
- `baseline` 인데 `[cvars]` 가 있으면 알린다. 거기 적은 값이 곧 '정상'의 정의가 되므로 학습과
  채점에 같은 값을 써야 한다.
- `probe` 면 매치를 시작하기 전에 해석 방법을 알린다. 세션이 끝난 뒤에 떠올리면 늦다.

용도는 `qa_scenario.json` 에 실려 세션 요약에 들어간다. 나중에 세션 파일만 봐도 그 숫자를
어떻게 읽어야 하는지 알 수 있다.

### 아직 남은 구멍

지금은 **모델이 어떤 조건에서 학습됐는지가 모델 파일에 기록되지 않는다.**
`models/anomaly.joblib` 은 학습된 파라미터만 담고 있어, 나중에 `baseline` 시나리오의 실력을
3에서 4로 바꾸면 모델과 조건이 조용히 어긋난다. 정상 플레이인데 오탐이 쏟아지는 형태로
나타나며, 원인을 모델이나 특징 설계에서 찾게 된다.

메우는 방법은 이미 이 프로젝트가 쓰고 있는 것과 같다. 세션 요약에 `config.as_dict()` 를 함께
남기는 것처럼, **모델을 저장할 때 학습에 쓴 시나리오를 함께 저장하면 된다.**

1. `tools/train_anomaly.py` 가 학습에 쓴 세션들의 요약에서 `scenario` 를 읽어
   `models/anomaly.meta.json` 에 남긴다.
2. 서버가 모델을 불러올 때 그 메타데이터를 함께 읽고, 현재 시나리오와 특징에 영향을 주는
   항목(맵·봇 수·실력·물리 cvar)을 비교한다.
3. 다르면 대시보드에 "학습 조건과 다름"을 표시한다. 끄지는 않는다. `probe` 에서는 다른 것이
   정상이기 때문이다.

## 5. 무엇이 만들어지는가

`tools/apply_scenario.py` 가 게임의 모드 폴더(`<홈패스>\qa`)에 세 파일을 만든다. 게임은 그
폴더를 검색 경로에 두고 있으므로 파일 이름만으로 실행할 수 있다.

| 파일 | 무엇인가 |
|---|---|
| `qa_match.cfg` | cvar 설정 → `map` → 대기 → 봇 투입 → 관전 전환까지의 전체 절차 |
| `qa_bots.cfg` | `addbot` 줄만 모은 파일 |
| `qa_scenario.json` | 확정된 시나리오. 서버가 읽어 세션 요약에 남긴다 |

게임은 `+exec qa_match.cfg` 로 시작하며 그 파일을 실행한다.

**cfg 를 놓는 폴더는 텔레메트리 경로에서 유도한다.** 게임이 텔레메트리를 쓰는 곳이 바로 모드
폴더이고 cfg 를 놓아야 하는 곳도 같은 폴더인데, 둘을 따로 설정하게 하면 한쪽만 고쳤을 때 게임이
cfg 를 못 찾는다. 그 실패는 게임 콘솔을 열어 봐야만 알 수 있으므로, `run_qa.bat` 에 이미 맞춰 둔
`TELEMETRY` 하나에서 나머지를 끌어낸다.

### 봇을 왜 따로 뺐는가

봇 투입은 이 절차에서 **유일하게 타이밍에 의존하는 부분**이라(6절) 드물게 실패할 수 있다.
그때 게임 콘솔에서 한 줄로 다시 시도할 수 있어야 한다.

```
\exec qa_bots.cfg
```

파일이 하나로 합쳐져 있으면 맵부터 다시 로드된다.

### `qa_match.cfg` 는 스스로 완결된다

게임을 켜 둔 채 콘솔에서 `\exec qa_match.cfg` 를 치면 같은 매치가 처음부터 다시 시작된다.
시나리오를 바꿔 가며 반복 시험할 때 게임을 껐다 켤 필요가 없다. 새 시나리오를 적용한 뒤
콘솔에서 이 한 줄만 치면 된다.

```
python tools/apply_scenario.py scenarios/skill_low.toml --telemetry "%APPDATA%\OpenArena\qa\qa_telemetry.jsonl" --game "C:\game\openarena-0.8.8"
```

맵이 다시 로드되면서 텔레메트리 파일이 잘리므로, 서버는 그것을 새 매치로 보고 세션을 새로
연다(`qa/tail_source.py`). 즉 시나리오 하나가 세션 하나에 대응한다.

## 6. 생성되는 cfg 의 구조

순서에 이유가 있다.

```
1. 맵 로드 전에 정해져야 하는 값     g_gametype, sv_maxclients, sv_pure, bot_enable, bot_minplayers
2. 매치 규칙                        fraglimit, timelimit, g_doWarmup
3. 시나리오 cvar                    [cvars] 에 적은 것
4. 결함 주입기                      qa_inject_* 4종 (적지 않은 것은 0으로)
5. 봇 정리 + 맵 로드                kick allbots → map <이름>
6. 대기                             wait 를 wait_frames 만큼
7. 봇 투입                          exec qa_bots.cfg
8. 관전 전환                        대기 후 team spectator
9. 키 바인딩                        [keys] 에 적은 것
```

**1번이 5번보다 위에 있어야 하는 이유**가 핵심이다. `g_gametype` 과 `sv_maxclients` 는
latched cvar 다. 즉 값을 바꿔도 곧바로 반영되지 않고 **맵이 로드되는 순간의 값으로 고정된다.**
`map` 뒤에 두면 이번 매치에는 반영되지 않고 다음 맵부터 적용된다. 이런 종류의 실패는 화면에
아무 오류도 남기지 않아 원인을 찾기 어렵다.

**4번이 5번보다 위에 있는 것**은 다른 이유다. 주입 cvar 는 latched 가 아니라 언제든 바꿀 수
있지만, 매치가 시작되기 전에 값이 확정돼 있어야 첫 프레임부터 의도한 상태로 기록된다.

**`map` 앞에 `kick allbots` 가 있는 이유**는 따로다. `map` 은 봇을 쫓아내지 않는다. 접속해
있던 클라이언트를 새 서버에 다시 붙이는데 봇도 클라이언트라 그대로 살아남는다. 그래서 이 파일을
두 번째로 실행하면 `addbot` 이 기존 봇 위에 얹혀 **인원이 두 배가 된다.** 자리가 찰 때까지
늘어난 뒤에는 조용히 멈추므로 화면에도 오류가 남지 않는다.

인원이 달라지면 교전 빈도가 달라지고 이상탐지가 배운 '정상'의 분포가 통째로 어긋난다. 실제로
이 문제로 오탐률이 일곱 배가 된 적이 있다(README '검증 결과').

## 7. 대기가 필요한 이유와 `wait` 를 늘어놓는 이유

`map` 명령이 돌아오면 서버는 떠 있다. 그런데 **사람 클라이언트가 그 서버에 접속을 마치기까지는
몇 프레임이 더 걸린다.** 그 전에 `addbot` 을 부르면 클라이언트 자리 배정이 겹칠 수 있다.
`team spectator` 는 더 확실하다. 접속이 끝나기 전에는 보낼 상대가 없어 그냥 사라진다.

그래서 `map` 과 `addbot` 사이에 대기를 넣는다. Quake3 계열에는 이 목적의 `wait` 명령이 있다.
명령 버퍼를 한 프레임 동안 멈춘다.

**한 줄짜리 `wait 150` 을 쓰지 않는 이유는 인자 지원이 엔진 갈래마다 다르기 때문이다.** 원래
`wait` 는 인자를 받지 않고 한 프레임만 기다렸고, 프레임 수를 받는 형태는 나중에 일부 갈래에
추가됐다. 인자를 모르는 엔진은 그것을 조용히 무시하고 한 프레임만 기다린다. 그러면 실패가
조용하다. 봇이 안 들어오는데 cfg 는 멀쩡해 보이고, 콘솔에도 아무 말이 없다.

`wait` 한 줄이 한 프레임이라는 동작은 어느 갈래에나 있다. 그래서 줄 수로 센다. 다만 150줄이
그대로 늘어서면 파일을 읽기 어려우므로 세미콜론으로 이어 붙여 한 줄에 25개씩 넣는다.
게임은 세미콜론도 명령 구분자로 보므로 동작은 같다.

```
wait;wait;wait;...(25개)
```

**대기는 시간이 아니라 프레임 수라는 점에 주의한다.** 실제로 얼마나 기다리는지는 프레임률에
달렸다. 초당 60프레임이면 150프레임은 2.5초, 초당 125프레임이면 1.2초다. 봇이 들어오지 않으면
`[timing] wait_frames` 를 늘린다.

## 8. 이름 검증

맵 이름이나 봇 이름이 틀리면 게임은 **조용히 실패한다.** 맵이 없으면 콘솔에 한 줄 찍고 이전
화면에 머물고, 봇 이름이 없으면 `Error: Bot 'X' not defined` 만 남기고 그 봇을 건너뛴다. 둘 다
게임 창을 보고 있지 않으면 알 수 없다. 자동 실행에서는 그사이 파이썬 쪽이 멀쩡히 돌고 있으므로
"대시보드는 켜졌는데 데이터가 안 들어온다"로만 보인다.

그래서 cfg 를 만들기 **전에** 실제 설치본을 뒤져 이름을 확인한다. 게임을 켜지 않고도 할 수 있는
이유는 게임 데이터가 담긴 `.pk3` 파일이 확장자만 바꾼 zip 이기 때문이다. 표준 라이브러리로
목록을 읽을 수 있고, zip 은 중앙 디렉터리만 읽으면 되므로 100MB 짜리 파일이어도 빠르다.

- 맵: 검색 경로 어디든 `maps/<이름>.bsp` 가 있으면 로드 가능하다.
- 봇: 게임이 `scripts/bots.txt` 와 `*.bot` 파일에서 봇 목록을 만든다. 같은 파일을 읽는다.

**조사에 실패한 경우와 이름이 정말 없는 경우를 구분한다.** 목록이 통째로 비어 있으면(경로를
모르거나 pk3 를 못 읽음) 이름 검사를 건너뛴다. 실제로 있는 이름을 없다고 막으면 사용자가
도구를 우회할 방법이 없는데, 그 실패는 반대 방향(없는 이름을 통과시킴)보다 나쁘다. 후자는
게임이 콘솔에 이유를 남기고 넘어간다.

같은 이유로, 여러 pk3 에 같은 파일이 있을 때 게임이 고르는 우선순위를 흉내 내지 않고 **찾은
것을 전부 합친다.** 우선순위 규칙을 잘못 흉내 내면 쓸 수 있는 이름을 막게 된다.

## 9. 자동 주입을 넣지 않은 이유

시나리오에 "60초에 끼임 주입을 켜고 70초에 끈다"를 적을 수 있으면 좋다. 시연에서 사람이 키를
누를 필요가 없고, 주입 구간의 시각이 정확해 검출 지연을 재는 데도 쓸 수 있다.

**cfg 로는 할 수 없다.** cfg 는 시작할 때 한 번 실행되는 명령 목록이고, 게임에는 "몇 초 뒤에
이 명령을 실행하라"는 기능이 없다. `wait` 는 프레임 수라 시간 기준이 아니고, 애초에 대기하는
동안 명령 버퍼 전체가 멈추므로 매치가 도는 중에 쓸 수 없다.

지금은 `[keys]` 로 키에 묶어 두고 사람이 누른다. 시연에서는 오히려 이쪽이 낫다. 언제 켰는지가
화면에 보이고, 정상 구간과 주입 구간이 한 세션 안에 함께 담긴다.

자동화하려면 **실행 중인 게임에 명령을 보낼 통로**가 필요하다. 방법은 있다. Quake3 계열 서버는
`rconpassword` 를 설정해 두면 UDP 로 콘솔 명령을 받는다. 다음과 같이 확장할 수 있다.

1. 생성된 cfg 에 `set rconpassword <임의 문자열>` 을 넣는다.
2. 파이썬 쪽이 서버 포트(기본 27960)로 `\xff\xff\xff\xffrcon <암호> <명령>` 형태의 UDP
   패킷을 보낸다. 응답이 오면 서버가 떠 있다는 뜻이므로, **봇 투입의 타이밍 의존(6절)도
   함께 사라진다.** 응답을 확인한 뒤에 보내면 되기 때문이다.
3. 시나리오에 `[[timeline]]` 절을 두어 `at = 60`, `command = "qa_inject_stuck 1"` 을 적고,
   드라이버가 시각에 맞춰 보낸다.

넣지 않은 이유는 지금 필요한 것이 "시작 조건을 정하는 일"이고 그것은 cfg 로 충분한데, rcon 은
네트워크 채널을 하나 더 만들어 실패 지점을 늘리기 때문이다. 필요해지면 위 순서로 붙인다.

## 10. 자주 걸리는 문제

**봇이 들어오지 않는다** — 먼저 게임 콘솔(`~`)을 열어 `Error: Bot 'X' not defined` 가 있는지
본다. 있으면 이름 문제이므로 `--list` 로 확인해 고친다. 그런 줄이 없으면 타이밍 문제이므로
`\exec qa_bots.cfg` 로 다시 시도해 본다. 그것으로 들어오면 `[timing] wait_frames` 를 늘린다.

**봇 이름 목록을 읽지 못했다고 나온다** — 설치본에서 봇 목록 파일을 찾았는지부터 본다.

```
python tools/apply_scenario.py --list --game "C:\game\openarena-0.8.8"
```

출력 끝에 원인이 나뉘어 나온다. 목록 파일 자체를 못 찾았으면 이름에 `bot` 이 들어간 파일들을
함께 보여 주므로 그중에 있는지 확인한다. 파일은 찾았는데 이름을 못 뽑았다면 표기가 예상과
다른 것이다. 어느 쪽이든 **시나리오에 `[[roster.bots]]` 로 이름을 직접 적으면 조사 없이
그대로 동작한다.** 이름은 게임의 Multiplayer > Add Bot 메뉴에서도 확인할 수 있다.

`count` 를 쓸 때만 조사가 필요하다. 이름을 전부 적어 두면 조사 결과와 무관하다.

**매치가 시작되지 않고 메인 메뉴에 머문다** — 맵 로드에 실패한 것이다. 콘솔에서 맵 이름을
확인한다. `--game` 을 주고 실행하면 이 경우는 cfg 를 만들기 전에 걸러진다.

**cfg 가 실행되지 않는다** — 게임이 `qa_match.cfg` 를 못 찾은 것이다. `run_qa.bat` 의
`TELEMETRY` 경로가 실제 홈패스와 맞는지 확인한다(`docs/setup.md` 4절). cfg 는 그 경로의
폴더에 생기고 게임도 같은 폴더에서 찾는다.

**봇이 시나리오보다 많다** — `map` 이 봇을 쫓아내지 않아 `\exec qa_match.cfg` 를 반복하면
봇이 쌓이던 문제였다. 생성되는 cfg 가 `map` 앞에서 `kick allbots` 로 정리하므로 지금은 생기지
않는다. 옛 cfg 가 게임의 모드 폴더에 남아 있으면 그것이 실행될 수 있으니, 도구를 다시 돌려
cfg 를 갱신한다. 실제 인원은 게임 콘솔의 `\status` 로 확인한다.

**봇 실력이 시나리오와 다르다** — 봇 실력은 스폰 시점에 정해진다. 이미 들어와 있는 봇에게는
반영되지 않는다. `\exec qa_match.cfg` 로 매치를 다시 시작한다.

**시나리오에 없는 봇이 들어와 있다** — `bot_minplayers` 가 남아 있는 경우다. 생성된 cfg 가
0으로 되돌리므로 보통은 생기지 않지만, 콘솔에서 직접 켰다면 그 값이 우선한다.

**`tomllib` 이 없다고 나온다** — 파이썬이 3.10 이하다. 3.11 이상을 쓰거나 `pip install tomli`
를 한다. `docs/setup.md` 8절의 conda 환경은 3.11이므로 그대로 따랐다면 걸리지 않는다.
